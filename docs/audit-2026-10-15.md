# Ревизия оригинальных архивов и реализации


**Follow-up:** [iteration 029](iteration-029.md) fixes the reproduced item/spell typed/raw validation gap and repeated inventory/armor/projectile metadata decoding. The item catalog now owns immutable definitions and cached frozen indices/rules. [Iteration 030](iteration-030.md) additionally fixes mutable collection ownership in canonical game/inventory snapshots and spell/recipe catalogs (AUD-04). [Iteration 031](iteration-031.md) removes inventory from flight state and adds canonical current-state projectile completion/reservations (AUD-05). This report records the pre-fix findings; broader original actor/action execution and unified content/evidence migration remain open.

Проверяемая версия: `c77b5b725b897554e23778dc8986350035261d5e`, после итерации 028. Цель — найти пропущенную функциональность, наши временные ограничения и лишнюю зависимость от устройства оригинала. Это аудит, а не новая реализация боёвки.

Короткие диагностические программы отдельно воспроизвели расхождения typed/raw и изменение старого снимка через общий массив. Существующие проверки проходят: 27 Python-тестов и 1945 C# cases с реальным 819-item каталогом (portable baseline — 1938). Они не отвергли найденные расхождения каталогов; это конкретный пробел покрытия, а не признак поломки уже работающих тестов.

## Находки

### AUD-01 — исполнитель оригинальных правил отсутствует, P1

**Подтверждённый интеграционный пробел.** `core/Game.cs` по-прежнему выполняет тестовую последовательность: сортировка Speed+Initiative, один противник, первая доступная цель, базовые кубики оружия либо Power. В `Game`/клиенте нет вызовов восстановленных `Original*` цепочек. `Hero`/`Enemy` не содержат канонических характеристик, истории классов, стамины, активных рук и полного состояния защиты.

Чистые формулы полезны и не требуют переписывания. Но мы слишком долго добавляли функции с входами «уже разрешённая характеристика/условие/цель», откладывая их производителей. Новая формула сама по себе не приближает Windows-сцену к оригинальному бою, если нет модели участников и общего исполнителя.

**Исправление:** отдельная модель оригинального участника и один путь command → eligibility/context → RNG → calculation → atomic state/events. Сначала ограниченный сквозной бой с явно заданными подтверждёнными фактами, затем расширение. Не приписывать старым тестовым сохранениям выдуманные оригинальные атрибуты. [TOC-41](https://linear.app/tochka/issue/TOC-41).

### AUD-02 — хеш исходной записи не защищает типизированные поля, P1

**Воспроизведённый дефект проверки данных.** В `core/Items.cs`, `NativeItems.cs` проверяются диапазоны, raw-хеш и часть native instance fields, но большинство дублирующих полей `ItemDefinition` не сравниваются с raw. На реальном каталоге изменение ToHit предмета 0 с 0 на 1 при неизменных RawRecordHex/RecordSha256 проходит `catalog.Validate()`.

В `core/SpellCatalog.cs` тот же класс дефекта: изменение Level на 9999 и RealmCode на -123 при прежних raw/хеше проходит Validate. Это не «взлом оригинала», а возможность получить внутренне противоречивый экспорт/модифицированный JSON и считать его проверенным источником. Для сравнения: `RecipeCatalog` уже сравнивает поля рецепта с соответствующими raw-байтами.

**Исправление:** единый декодер при импорте; либо строить typed fields из проверенной записи, либо сравнивать все известные дублирующие поля. Политика неизвестных кодов должна явно сохранять unknown, а не объявлять невозможное значение подтверждённым. Runtime-каталог и evidence отделить. [TOC-40](https://linear.app/tochka/issue/TOC-40).

### AUD-03 — импортные байты и проверка целого каталога остаются на обычном пути, P2

**Подтверждённый технический долг.** `Inventory.Rules(catalog)` каждый раз проходит все определения через `OriginalItemAdapter.Rule`; там снова выполняются hex decode и SHA-256. `Inventory.Validate`, `CreateItems`, `Commit` и операции UI повторяют этот путь. Даже изменение одного стека заново пересобирает правила всего каталога. `OriginalDefenseAdapter` также извлекает signed armor из raw на подготовке, вместо готового семантического поля.

Локально 10 перестроений правил для 819 предметов заняли около 55 ms. Это диагностическое измерение данного окружения, не production/mobile benchmark; проблема подтверждается прежде всего самим графом вызовов. Не требуется доказывать заметный лаг, чтобы убрать повторное декодирование неизменных определений.

**Исправление:** один validated/compiled content set с индексами по ID, inventory rules, armor, weapon/ammo capabilities и исходными свидетельствами отдельно. Операции проверяют изменяемое состояние, а не весь исходный архив. Кешировать поверх публично изменяемых массивов нельзя — сначала определить владение данными. [TOC-40](https://linear.app/tochka/issue/TOC-40).

### AUD-04 — record-снимки не являются глубоко неизменяемыми, P2

**Воспроизведённая слабость контракта.** `GameState.Party`, `ItemInventoryState.Items`, каталоги, навыки и эффекты — публичные массивы. `var newer = old with { Round = 1 }; newer.Party[0] = ...` меняет также `old.Party[0]`. Диагностика получила `old.Power=123` после изменения нового снимка.

Текущие переходы во многих местах явно копируют массивы; аудит не обнаружил этим способом потери пользовательских предметов в текущем UI. Но формулировка «immutable record-based state» сильнее фактической гарантии. Асинхронные callbacks, previews, кеши и replay будут полагаться именно на неё.

**Исправление:** immutable collections либо строгое владение с защитным копированием и закрытыми массивами. Проверять неизменность предыдущего снимка через внешний alias, а не только аккуратность одного метода. [TOC-42](https://linear.app/tochka/issue/TOC-42).

### AUD-05 — у полёта снаряда собственный полный снимок инвентаря, P1 до интеграции

**Архитектурный риск, не наблюдавшаяся потеря данных.** `ProjectileSeriesState` содержит Inventory и возвращает изменённую копию; у игры уже есть `GameState.Items`. `OriginalProjectileAttack.Complete` не принимает текущий GameState и не применяет HP. Если будущий исполнитель запишет старый flight inventory обратно целиком, несвязанные изменения инвентаря между launch и completion могут исчезнуть.

Сейчас эти подсистемы не соединены, поэтому называть это существующим багом живого боя было бы неверно. Но соединять их простым присваиванием нельзя.

**Исправление:** один владелец текущего инвентаря; flight хранит источник/резервацию, ordinal и необходимые снимки атаки. Completion проверяет актуальную версию/владение и применяет расход/HP/события одной транзакцией, сохраняя посторонние изменения. Нужны тесты save/load, interruption, двукратного callback и изменения другого предмета в полёте. [TOC-42](https://linear.app/tochka/issue/TOC-42).

### AUD-06 — доступный контент почти не доведён до игрового исполнения, P1

**Подтверждённые пробелы.** Файлы ниже были перечислены ещё в `docs/formats.md`; это не вновь открытые базы. В репозитории нет законченных декодеров/исполнителей этих систем:

| Доступный источник DATA.SLF | Что требуется исследовать/подключить |
|---|---|
| MONSTERS.DBS | Семантические определения монстров для участников боя |
| ENCOUNTERTABLES.DBS | Данные встреч и выбор состава |
| ITEMTABLES.DBS | Табличные источники предметов; точное loot/shop назначение ещё подтвердить |
| MISSILETABLES.DBS | Определения снарядов и связь с доставкой/попаданием |
| NPC.DBS, FACT.DBS, 165 файлов NSF в NPC SCRIPTS | NPC, факты/события, диалоги и зависимости; полный формат/семантика ещё не установлены |
| LEVELS.DBS | Реестр/метаданные локаций; это не геометрия LEVELS.SLF |

Наличие файлов не доказывает уже понятную схему, число игровых сущностей или расположение всех quest rules. В частности, 165 NSF — число файлов, не утверждение о числе NPC. Эти направления не заблокированы размером LEVELS.SLF. [TOC-43](https://linear.app/tochka/issue/TOC-43).

Магия: `SpellCatalog` показывает оригинальные метаданные, а `Magic.cs` выполняет пять synthetic spells. Один полный original damage/healing effect всё ещё не замкнут. SPELLEFFECT.DBS уже исследовался: одинаковые наблюдавшиеся записи не дают оснований считать его готовым хранилищем формул.

Крафт: 36 reference recipes и native arithmetic существуют, но `Crafting.Denial` запрещает любой не-fixture каталог. Реальный рецепт через игровое меню не исполняется. Мягкий реворк меню TOC-22 не должен заменять подключение базовой оригинальной комбинации.

Экипировка: live `Equipment.WeaponSlot` допускает один melee weapon; полный armor/shield/offhand/alternate-hand resolver отсутствует. Отдельный defense adapter не означает, что герой уже может носить и сохранять эти комплекты.

Прогрессия/мир: канонические XP/level/class/skill progression, встречи и несколько целей, NPC торговля/отношения, факты/quest dependencies и реальное устранение Crock solo blocker не реализованы тестовыми XP/captivity/keeper fixtures. Часть работы корректно отложена по этапам; важно не считать её закрытой числом арифметических проверок.

### AUD-07 — сохранение привязано к fixture и одному item hash, P2 до смены модели

**Планируемый интеграционный долг.** `ClientSave` хранит камеру, GameState и ItemDatabaseHash; нет отдельной идентичности ruleset/content set, полного actor/action/pending-flight состояния. Жёсткие границы камеры в `LoadFrom` относятся к тестовому коридору. Это не универсальный сейв оригинального мира.

**Исправление:** явный save contract для нового режима симуляции, identity/version content/rules и последовательное восстановление RNG/действий. Сохранить нынешнюю аккуратную миграцию fixture без автоматического добавления придуманных характеристик. Не расширять каждый новый actor факт очередным nullable хвостом старого Hero. [TOC-42](https://linear.app/tochka/issue/TOC-42).

### AUD-08 — диапазон/состояние действий определяет UI, P2 до интеграции

**Подтверждённая временная реализация.** `client/Main.cs` проверяет DistanceTo <=4.5 отдельно при действии, построении меню и очереди. `Game.ResolveRound` не знает позиции/range/LOS; клиент содержит также сохранения, контроллер, построение диалогов и smoke-код. Это не перенесённый native костыль, а наш prototype.

**Исправление:** authoritative action availability и preview в общем resolver; клиент только отображает результат. Разделить presentation, command controller и save boundary по ответственности, без переписывания рабочего HUD ради косметики. [TOC-41](https://linear.app/tochka/issue/TOC-41).

### AUD-09 — роадмап и метрика прогресса отстали от кода, P2

**Подтверждённая ошибка учёта.** Верх роадмапа всё ещё объявлял baseline 025 и относил monster defense/location к отсутствующим, хотя низ страницы уже дошёл до 028. Аритметические case counts, включая exhaustive loops, не измеряют число законченных игровых механизмов.

Исправлено в этой ревизии: summary/matrix синхронизированы с 028, добавлен приоритет интеграционных задач. Отдельно учитывать: helper evidence, typed import, command execution, persistence, UI и оригинальное поведение. Existing tests/CI остаются полезными; без original runtime captures они не доказывают точное совпадение игры. Физически запускаемый Windows preview сегодня проверяет fixture-сцену.

## Что переносить заново не нужно

- Канонический инвентарь уже использует ID, quantity/resource и location. Его целочисленные количества и атомарные операции не требуют native 12-byte slots, 500-slot bounds или старой переброски предметов.
- `Research/NativeInventory`/`NativeStacks` остаются исследовательскими моделями; клиент не вызывает их. Их наличие само по себе не означает две активные игровые системы владения.
- Native ID/icon dispatch в явно названных адаптерах — допустимое свидетельство baseline. Следующий шаг — компиляция семантических runtime capabilities, а не удаление подтверждённых исключений из оригинальных формул.
- Двойное K в penetration, signed armor и положительная monster fatigue поправка сохранены осознанно по EXE и пользовательскому решению использовать старые формулы. Это не основание копировать старые глобальные структуры и не повод молча менять баланс.
- Source/patch precedence, сохранение исходного файла при неудачной загрузке, atomic save и проверяемый Windows updater имеют полезные границы и проверки; аудит не выявил причин переделывать их целиком.

## Новый порядок ближайшей работы

1. TOC-40: закрыть typed/raw integrity и компилировать неизменяемые runtime definitions один раз.
2. TOC-41 + TOC-42: определить actor/action/save contracts и единственное владение состоянием; подключить один оригинальный сквозной бой, включая реальный расход ресурса и deterministic continuation.
3. В том же вертикальном срезе выполнить один original magic effect и одну native combination; затем расширять покрытие. Не наращивать новые изолированные helper APIs без назначенного потребителя.
4. TOC-43: импорт доступных monster/encounter/item/missile данных; NPC/facts/dialogue вести отдельным content track. Геометрия ждёт локальной инвентаризации LEVELS.SLF, а остальные данные — нет.
5. Сохранить самостоятельные пользовательские redesign задачи TOC-22/23/24. Здесь не принимаются новые балансные решения.

В этой ревизии исправлена документация и заведены задачи. Выявленные дефекты исходного кода ещё не исправлены; игровых изменений и новой Windows-сборки из аудита не следует.
