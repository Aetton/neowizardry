# Iteration 022 — ammunition compatibility, refill and continuation

Recovered `0x51C8F0` definition compatibility: ordinary launcher families, conditional candidate-range checks, and all twelve Omnigun definition stages. Stage dispatch uses definition IDs 599–610; actor-level upgrade policy remains separate. Recovered the five weapon/fuel pairs, including the distinction between refill support and compatibility dispatch. These are original baseline rules, not the deferred Gadgeteer/Omnigun redesign.

Recovered deterministic refill `0x51E9F0`: maximum signed-constant/dice amount, transfer the smaller of missing capacity and available fuel units, spend one unit per shot restored. No RNG. Empty-fuel retention follows the capability predicate already traced in 021. Clean inventory transfers are atomic and keep surplus; unsafe native byte overflow/underflow is rejected. Private aggregate inspection found four relevant mode-4 weapons with valid capacities and fuel modes 1/2; proprietary rows stay private.

Added `OriginalAmmunitionAdapter`, strict compatibility in `OriginalWeaponAdapter.PreparePrimary`, `ItemInventory.RefillResource`, and `OriginalProjectileReload`. Reserve replacement prefers the explicitly selected compatible reserve, then searches for the previous ammo definition in a caller-supplied accessible order. Fuel refill uses an explicit source or the first matching nonempty source in an explicitly ordered reserve list. There is no native-slot emulation or implicit scan of other actors' inventories.

Added `ProjectileSeries.ReplaceDepletedSource`: reload continues the same series/ordinal/remaining allocation without rerolling swings. Actor/target interruption now takes priority over simultaneous resource depletion, so adding ammo cannot revive an interrupted action. In-flight and completed series cannot resume via reload. A changed preferred ammo definition requires preparing the next projectile from the new source rather than retaining the old ammo dice/accuracy.

Validation: 893 portable C# checks including gestures (186 added), 900 with the private 819-item catalog, 894 with private spell metadata/power scenarios (826 combinations, not actor eligibility). 27 Python tests pass. Client build has zero warnings/errors. Real-data Godot gameplay and synthetic mobile smokes pass. Tests cover launcher mismatches, each Omnigun stage and family boundary, range conditions, distinct refill/compatibility tables, capacity arithmetic, partial/full/empty transfer, quantity and charge fuel, empty retention, preferred/fallback selection, stale reserve IDs, conserved leftovers, no resource-based resurrection, stale completion after replacement and deterministic depleted/pending save replay.

Scope: callable independent-core behavior; live Godot training battle remains a labelled fixture. The native code attempts reload before final swing/actor checks, even after the last projectile. These series helpers only resume Depleted series with remaining swings; complete end-of-attack/incapacitation refill scheduling still belongs to the future full attack controller. Actor ownership/equipment/curse policy, projectile contact, retargeting, thrown opposite-hand redistribution, spell-use and nonstack throwing remain open. No runtime comparison against the original executable is claimed.
