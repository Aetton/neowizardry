# Architecture

`core/` contains immutable record-based transitions with no Godot dependency. It owns party state, round ordering, XP distribution, captivity and versioned serialization. `client/` references the core and owns 3D scene, collision, camera, UI and user data storage. `tools/` reads originals locally and produces inventories/catalogs/extracted assets under ignored paths.

The UI currently exposes 1–8 characters, with no six-character assumption in the core. The maximum is a prototype constraint, not the final design promise. Enemy parameters are independent of party size. Renderer timing does not affect combat order. `Magic.cs` owns synthetic spell definitions, target/order validation and realm pool spending. Each selected spell replaces its actor's physical attack inside the shared queue; multiple actors may receive orders in one round; skipped/dead actions consume neither mana nor RNG.

New expeditions use the recovered ordinary character melee path described in [iteration 032](iteration-032.md). A persisted MeleeEncounter supplies authored effective character facts and references real owned weapons in the canonical inventory. Game.Attack dispatches its current state to MeleeCombat.Advance; core validates reach/eligibility and commits recovered attack/swing, contact/penetration/damage, HP, RNG and scenario rewards. The opponent is a character training fixture, not an imported monster. New parties use recovered character initiative and ordinary single-hand attack-group continuation (033); earlier saved facts retain their former Speed policy. First-eligible targeting, ties, prototype RNG, immediate room delivery and training XP remain authored scenario policies. Frost / Energy Blast with ordinary risk outcomes and Heal Wounds use the same executor with explicit saved caster/resistance facts. General actor creation/stat derivation, monster execution, conditions, ranged delivery, native casting reactions/progression, broader effects and combinations remain open. Legacy saves and the Spell sandbox retain the old labelled executor; restored melee never silently falls back to it.

Current dialogue is one fixed synthetic keeper response, with no LLM and no canonical NPC data. Captivity is an explicit state transition demonstrating solo recoverability. It is not a quest parser or a reproduction of Crock. The item browser now consumes imported schema-3 catalogs (with schema-2 read compatibility); equipment moves a specific owned instance between the shared party bag and the hero weapon location, returning the previous instance on a swap. Original restriction flags remain enforced. Instance IDs, quantities, resource counters and locations survive saves; configured test loot is granted once with victory.

Import pipeline preserves source hashes and raw codes instead of guessing meanings. `Resources` implements ordinary loose-file and numbered-patch precedence with source provenance; Parallel Worlds and localization remain out of scope. Imported catalogs feed the equipment inspector and base melee rolls.

Windows is the primary manual test platform. Its CI exports the shared client, tests the exported executable and publishes immutable previews. The PowerShell launcher validates package hashes and keeps build files separate from Godot user-data saves. Android exports are manually triggered for mobile-specific checks and milestones.

Source assets, full exported tables and local source paths must remain outside public git. Research reports may contain hashes, aggregate counts and format offsets; the actual content stays in the user's private asset storage.

`Crafting.cs` provides atomic fixture recipes over instances in the shared bag, with saved skill and knowledge gates. Fixture recipe IDs apply only to the synthetic catalog. Magic effects persist on hero/enemy records; the core ticks them at a documented round boundary and resolves periodic victory through the existing reward path. These mechanisms do not establish original crafting or status rules.

`tools/spells.py` exports independently sourced table/description metadata and preserves unknown raw spell bytes. `SpellCatalog.cs` validates the read-only reference separately from `Magic.cs`: original numeric IDs do not enter the synthetic learned spellbook or execute combat rules. Public builds contain only an invented reference fixture, while full exports remain local.


## Inventory boundary — decision 2026-10-15

Reproduce gameplay capabilities on a clean model; do not reproduce the original storage layout or accidental repair/move behavior as runtime rules. `ItemInventory.cs` defines the target instance inventory: stable IDs, definition IDs, quantities, identification, explicit resource counters, curse state and one location per instance (container or equipment slot). Rules specify stack limits and resource kinds. Transfers preserve item properties; splitting/merging conserves quantity; equipment locations cannot overlap; recipe consumption/production validates the entire resulting state before returning it. Exhausting charges leaves the item present. Quantities/resources use integers, capacity is configurable, and runtime serialization contains no original slot bytes or provenance hashes.

`OriginalItemAdapter.cs` converts supported original data into this model and returns raw evidence separately. It refuses unresolved counter inconsistencies, overflow and unsupported curse flags. Original-format repairs are an import decision, never an automatic gameplay side effect. The original +10 field's full behavior still requires research; the adapter's accepted 0/1 interpretation follows the documented editor interpretation, not proof of every curse mechanic.

`Research/NativeStacks.cs` and `Research/NativeInventory.cs` are original-format research utilities, not a second gameplay inventory. Their slot-indexed snapshots exist to verify recovered behavior and local combinations. Neither the client nor canonical inventory depends on them. They deliberately guard against data loss even where the original discarded overflow or unchecked metadata.

Integration status (iteration 016): `GameState.Items` is the single authoritative inventory. Heroes have no duplicate equipped-definition field; equipment and combat query the instance at the hero weapon location. The aggregate `GameState.Bag` has been removed. `Inventory` provides gameplay operations and deterministic allocation using the saved `NextItemSequence`; item creation uses semantic rules and the saved prototype RNG for initial resource rolls, without constructing original slot bytes. Stack output packing is part of the atomic final-state transaction. The Items UI selects an individual spare instance and provides split/merge actions. Fixture crafting selects matching bag instances in stable ID order and cannot consume equipped copies. The larger crafting menu/instance-selection redesign remains deferred.

Game saves use schema 5. Schema-4 duels migrate intact; tactical fields require schema 5 and older saves receive no invented positions. Schema-3 projectiles migrate intact and older saves retain legacy combat without fabricated Melee facts. Schemas 1/2 reject new projectile fields; schemas 1/2/3 reject new melee fields. `GameSaveMigration` alone reads schema-1 `Bag`/hero `EquippedItemId` fields and deterministically produces one instance inventory. Item-bearing legacy saves require a catalog; known stack limits split old aggregate quantities without losing units. Legacy items are identified, matching their former prototype behavior. Missing historical resource counters initialize to zero, with no RNG advance or free refill; original SAV/CHR import is a separate feature. Existing malformed or over-capacity legacy data is rejected, never silently truncated. Current saves reject obsolete ownership fields. Client loading checks the wrapper's database hash and camera before applying state, leaves source bytes untouched, and blocks background autosave after a failed load until a valid load or an explicit new expedition.

Schema-2 item catalogs lack native modes. Their compatibility rules use separate melee-weapon copies and aggregate nonweapon stacks, with no inferred charge pool. New original imports should use schema 3. The game starts with a configurable 4096-instance prototype capacity as an allocation guard, not the original 500-slot bound or a final balance choice; the independent instance core imposes no such default limit. Item resource spending exists in core, but wand/gadget use effects, recharge, curse enforcement/removal and native live crafting are still unimplemented.


## Combat and magic formula boundary

User decision, 2026-10-15: original formulas are the baseline, implemented as independent typed rules. `core/Rules` owns verified local arithmetic with explicit inputs and resolved random draws; it has no Godot, original memory offsets or `GameState` dependency. Actor/class/skill and condition derivation, command eligibility, RNG allocation, state-changing effects and UI remain separate responsibilities. Pure previews use the same formula functions without spending resources or randomness.

Iteration 017 adds a scoped single-weapon physical attack budget and original magic arithmetic; see [physical evidence](original-combat-formulas.md) and [magic evidence](original-magic-formulas.md). The existing playable sentinel still uses documented fixture rules. Wiring recovered math into incomplete actors would require inventing original attributes, class histories and contextual rules, so live replacement follows those data and resolver implementations. TOC-23 and other deliberate redesigns are explicit later changes, not hidden reinterpretations of the recovered baseline.


## Projectile action ownership — iteration 031

GameState.Items is the sole inventory. Its immutable ProjectileActions dictionary stores actor/content/ruleset identity and series state; a pending series stores one source-instance reservation, ordinal and resolved aim, never a second inventory. ProjectileExecution completes resource cost, actual-target HP and the cleared/advanced pending action in one transition against current state. Canonical inventory commits validate pending sources, so unrelated changes survive while conflicting changes fail. Action IDs use a persisted high-water counter, and callbacks validate the current action ordinal. The owner must serialize state commits or compare-and-swap: the pure API does not make stale snapshot assignment safe. Schema-3 pending saves require their catalog and supported ruleset; aim is loaded without re-running spread/RNG. Original actor/stat/eligibility/collision producers and reward scheduling remain external; see [iteration 031](iteration-031.md).
